Vínculo entre vendedor (Omie) e funcionário (RH)

Hoje o Hub sincroniza vendedores de duas contas Omie (Mogi e Uberaba) numa tabela própria, mas sem ligação com core.funcionarios — cargo, setor e unidade de RH ficam de fora. Uns 5 vendedores vendem nas duas contas ao mesmo tempo, cada um com um codigo_vendedor_omie diferente por conta. Isto aqui é uma proposta de como resolver isso de forma automatizável, com o mínimo de trabalho manual possível — pra ver, testar e discutir antes de eu mexer em qualquer coisa de verdade.

1

O que já existe hoje

Investiguei o dump do banco antes de propor qualquer coisa nova — e a boa notícia é que metade do caminho já está pavimentada, só não está sendo usada.

Existe, pronta, sem uso

vendedores.id_funcionario

Cada linha de core_vendas_faturamento.vendedores (uma por conta Omie) já tem uma coluna id_funcionario, com FK de verdade pra core.funcionarios(id) e índice:

  • fk_vendedores_id_funcionario ... ON DELETE SET NULL
  • idx_vendedores_id_funcionario
  • Sem UNIQUE nela — várias linhas de vendedores (ex: Mogi + Uberaba) podem apontar pro mesmo funcionário. É exatamente o caso dos 5.

Nenhuma das views/functions de ranking usa essa coluna hoje.

Usada em produção, mas solta

pessoa_vendedor

Tabela separada: nome text + codigos_vendedor text[] (array de strings tipo "<codigo_empresa>:<codigo_vendedor_omie>"). É o que fn_ranking_vendedores_vendas/faturamento e fn_detalhe_vendedor_vendas/faturamento usam pra juntar as duas contas de uma mesma pessoa hoje.

  • Mantida manualmente, por texto — sem link com core.funcionarios.
  • Match por nome exato, sem CPF, cargo, setor, foto.
  • Vendedor não mapeado cai em 'sem_mapa:'||empresa||':'||codigo no ranking — funciona, mas aparece "solto".
A proposta central: não criar uma terceira estrutura. Migrar o que pessoa_vendedor faz hoje pra vendedores.id_funcionario, que já é mais forte (FK real, ganha cargo/setor/foto de graça) e já existe. O "dicionário" que você pediu é essa própria coluna — falta só a tela pra preenchê-la.

3

SQL

Duas partes: um backfill que aproveita o pessoa_vendedor já preenchido hoje pra popular id_funcionario sem trabalho manual nenhum onde o nome já bate; e a troca do JOIN nas 4 funções de ranking/detalhe.

backfill_id_funcionario.sqlroda uma vez, antes de ligar a tela
-- 1) Cria funcionário pra quem já tem "pessoa_vendedor" mas ainda não tem
--    core.funcionarios (heurística por nome — o que não bater cai na fila da tela)
INSERT INTO core.funcionarios (nome_completo, id_cargo, id_setor, codigo_empresa)
SELECT DISTINCT pv.nome, :id_cargo_vendedor, :id_setor_vendas, v.codigo_empresa
FROM core_vendas_faturamento.pessoa_vendedor pv
JOIN LATERAL unnest(pv.codigos_vendedor) AS codigo(val) ON TRUE
JOIN core_vendas_faturamento.vendedores v
  ON v.codigo_empresa::text || ':' || v.codigo_vendedor_omie = codigo.val
WHERE pv.deleted_at IS NULL
  AND NOT EXISTS (
    SELECT 1 FROM core.funcionarios f WHERE f.nome_completo = pv.nome
  );

-- 2) Aponta cada linha de vendedores pro funcionario correspondente
UPDATE core_vendas_faturamento.vendedores v
SET id_funcionario = f.id
FROM core_vendas_faturamento.pessoa_vendedor pv
JOIN LATERAL unnest(pv.codigos_vendedor) AS codigo(val) ON TRUE
JOIN core.funcionarios f ON f.nome_completo = pv.nome
WHERE pv.deleted_at IS NULL
  AND v.codigo_empresa::text || ':' || v.codigo_vendedor_omie = codigo.val
  AND v.id_funcionario IS NULL;

-- 3) O que sobrar com id_funcionario NULL é exatamente a fila
--    inicial da tela de vínculo (seção 5) — nada se perde, só falta decidir.
fn_ranking_vendedores_vendas — troca do JOINmesmo padrão nas outras 3 funções
- LEFT JOIN core_vendas_faturamento.pessoa_vendedor pv
-   ON (b.codigo_empresa::text || ':' || b.cod_vendedor) = ANY (pv.codigos_vendedor)
-   AND pv.deleted_at IS NULL
- -- identidade = COALESCE(pv.id::text, 'sem_mapa:'||empresa||':'||codigo)
- -- vendedor   = COALESCE(pv.nome, b.vendedor)+ LEFT JOIN core_vendas_faturamento.vendedores vd
+   ON vd.codigo_empresa = b.codigo_empresa AND vd.codigo_vendedor_omie = b.cod_vendedor
+ LEFT JOIN core.funcionarios f ON f.id = vd.id_funcionario
+ -- identidade = COALESCE(vd.id_funcionario::text, 'sem_mapa:'||empresa||':'||codigo)
+ -- vendedor   = COALESCE(f.nome_completo, b.vendedor)
+ -- de graça: f.id_cargo, f.id_setor, f.codigo_empresa (unidade "de casa")
pessoa_vendedor não precisa ser dropada no mesmo dia — dá pra rodar as duas versões da função em paralelo (uma view de comparação, id_pessoa antigo vs. id_funcionario novo) por um mês fechado, conferir que os números batem, e só então trocar de vez e arquivar a tabela.

API (Next.js → api-acos-vital)

Mesmo padrão de proxy já usado em todo o Hub — nada de acesso direto ao banco pelo Next.js.

RotaO que faz
GET /api/vendedores?status=pendente Lista vendedores das duas contas Omie. status: pendente (id_funcionario null), vinculado, ou omitido (todos). Cada item já vem com nome/cargo/setor quando vinculado.
GET /api/vendedores/sugestoes?codigo_empresa=..&codigo_vendedor_omie=.. Sugestão de match: mesmo nome já vinculado em outra unidade, ou funcionário com nome parecido (unaccent + similarity(), mesmo estilo do ILIKE já usado em blacklist_vendedores).
PUT /api/vendedores/:codigoEmpresa/:codigoVendedorOmie Body { id_funcionario }. Grava o vínculo (ou desfaz, com null).
POST /api/funcionarios Já existe — reaproveitado como atalho de "criar funcionário" direto da fila, pré-preenchido com o nome vindo do Omie.

Protótipo — tela de vínculo

Dados fictícios (nomes parecidos com os que já aparecem no ranking real), mas totalmente clicável — abra um card pendente, veja a sugestão, vincule.

hub.acosvital.com.br/cadastros/auxiliares/vendedores

Vínculo de Vendedores

Vendedores sincronizados do Omie (Mogi + Uberaba) × funcionários do RH

Pontos em aberto pra debater

  • Vendedor sem funcionário correspondente (representante externo, ex-funcionário de antes do módulo de RH): a fila vai cobrar vínculo pra sempre? Proposta em aberto — um botão "sem vínculo, ignorar" que marca a linha como decidida sem exigir id_funcionario.
  • id_usuario também poderia auto-sugerir: se o funcionário escolhido já tem login (auth.usuarios.id_funcionario), a tela poderia oferecer linkar vendedores.id_usuario junto, no mesmo clique.
  • Confiança da sugestão automática: nome idêntico entre as duas contas é forte; nome parecido (via similarity()) precisa de um corte — vale a pena eu trazer números reais do pg_trgm antes de fixar um threshold.
  • Quando aposentar pessoa_vendedor de vez: sugiro só depois de um mês fechado batendo 100% entre as duas versões da função de ranking.
